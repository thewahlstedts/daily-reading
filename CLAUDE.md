# Daily Reading

Installable web app (PWA) for a one-year Bible reading plan, built for a group that meets weekly to review the week's readings: weekly progress, read-aloud, themes, reading-text options, shareable schedule (start date + meeting day), and optional cross-device sync.

Live: https://thewahlstedts.github.io/daily-reading/ (GitHub Pages, served from `main`, root). Pushing to `main` deploys in about a minute.

## Architecture

Plain static files, no build step, no package manager. Classic `<script>` tags share one global scope, loaded in this order:

| File | Role |
|---|---|
| `theme-init.js` | Runs in `<head>` before paint: applies saved theme |
| `vendor/supabase-2.117.1.js` | Pinned supabase-js UMD build (vendored so it works offline and can't change under us) |
| `app.js` | Everything else: `state` + `save()`, plan parsing, rendering, reader, speech, settings, themes, reading text, sharing |
| `sync.js` | Optional Supabase sync and the Account screen (`#account`); hooks in via `window.onStateSaved`; exposes `sendSignInLink` / `signInWithCode` / `getAccessToken` / `currentUserEmail` |
| `reminder.js` | Daily reminder (Web Push), Settings → Reminder. Per device: subscribes, then upserts the subscription, time and time zone into `public.reminders`; hidden while `VAPID_PUBLIC_KEY` is empty. Uses `window.supabaseClient` / `currentUserId()` from `sync.js`, re-saves once per load on `authchange`, and removes the device's row in `window.beforeSignOut` |
| `onboarding.js` | First-visit walkthrough (sign-in, meeting day, start date + week preview, translation, AI for questions, look, share). Borrows `#theme-picker` / `#text-options` from Settings while open. Starts via `planReady`; current step persists in `daily-reading:onboard-step` so the email-link round trip resumes it. Arriving from a share link sets `daily-reading:invite`, which turns the welcome into a "You're invited" view. |
| `sw.js` | Service worker: shows reminder `push` notifications (opens the app on click, never a URL from the payload; `badge-96.png`, rendered from `badge.svg`, is the Android status-bar icon); app shell network-first (`cache: 'no-cache'`), falling back to the cache after 4 s (then cache-first for the rest of that load); bible.helloao.org responses and `bibles/` cache-first |
| `plan.txt` | The plan: one reading per line, `Book N` or `Book N-M` |

- **State:** one `state` object in localStorage (`daily-reading:v1`), always passed through `sanitizeState()`. Add new fields to `defaults` *and* `sanitizeState()`.
- **Schedule:** reading `i` is due on `start + i` days. "Next" is the first unread index.
- **Group weeks:** with `meetDay` set (0 = Sun … 6 = Sat), a week runs from the day after one meeting through the next meeting day (`weekWindow()`). Only unread readings *before* the current week count as behind (`dueBefore()`). The plan is 52 weeks of 7 readings; plan week N (`planWeek()`, readings 7(N−1)…7N−1) is the same for every group, so weekly material is keyed to it, and the week section's title shows it ("This week · Week 6", just "Week 9" further out, or "Weeks 6–7" when the start isn't aligned). A start on the day after the meeting day makes each group week one plan week (`isAligned()`): changing the meeting day in Settings moves the start to the nearest aligned day (`nearestAligned()`, ±3 days, with Undo), and Settings shows `#align-note` with a fix when a hand-picked or shared start doesn't line up. Shared start dates are never moved automatically, since the whole group uses them. The home page shows the current week (without a group, an "Up next" preview of 6 readings); the whole plan is in Settings → Full plan (`#plan` sheet, `renderPlan()`), unread readings by month with a "Show completed" toggle (`state.showCompleted`).
- **Week summaries:** `summaries/week-01.txt` … `week-52.txt`, one per plan week, plain text with blank-line paragraphs, rendered with `textContent` in the `#summary` sheet (`openSummary()`) in the reader's reading-text size and alignment. Where the button shows depends on the moment: before any reading of a week is done, the today card offers that week's summary next to Read/Listen (`startingSummary()`); on meeting day, the `#meeting-card` holds the week's summary and verses to discuss (`renderMeeting()`): below the today card while the week has unread readings, above it once the week is read; then the next reading is next week's, so the today card stays hidden until the meeting card is closed. Its close button (top right) asks first (`#meeting-dialog`), then sets `state.metOn` (synced) to today, which hides the card for the day (`meetingToday()`), moves its buttons back to the week section ("Met today") and lets the today card offer next week's summary; otherwise the week section's button opens the summary for the plan week holding most of the viewed group week's readings (`summaryWeek()`), and without a group `#summary-entry` opens the one for the next reading's plan week. A summary shown in a card isn't repeated below. Meeting day means the day itself (there's no meeting time); don't suggest setting the day before as the meeting day for prep, since `meetDay` defines the weeks and is shared with the group. Buttons only appear once the file has loaded (`loadSummary()`). All 52 are in `SHELL_FILES`, so every one must exist (a missing file breaks the service worker install) and changing one means bumping `SHELL`. How they're written and checked is in `summaries/GUIDE.md`; `tools/week_text.py <N>` prints a week's LEB text verse by verse for writing and checking. Each summary is also narrated in the LEB's voice (`tools/narrate_leb.py OUT --summaries`, writing `OUT/summaries/week-NN.m4a` + `.json` with paragraph start times and the text's SHA-1; only weeks whose text changed are redone), uploaded to R2 under `summaries/`. The sheet's Listen button (`#summary-play`) appears only online and when the recording's hash matches the loaded text, so an edited summary hides it until it's re-narrated and re-uploaded; playback highlights the current paragraph.
- **Scripture:** from the Free Use Bible API (bible.helloao.org, no key), one chapter per request; `BIBLES` lists the offered translations (`src` = HelloAO id) and `BOOK_CODES` maps plan book names to USFM codes.
- **Licensed translations (NIV, NLT, AMP):** `licensed: true` in `BIBLES`. Text comes from API.Bible via the Supabase Edge Function `supabase/functions/scripture` (holds `API_BIBLE_KEY`; only serves signed-in users; Bible IDs allowlisted in `BIBLES` there). Starter plan: max 3 licensed Bibles, 5,000 requests/month, non-commercial only. Client must show the returned `copyright` and report `fumsToken` to FUMS (`reportFums()`, GET `https://fums.api.bible/f3`). Licensed text is kept in memory only (never cached to disk or the service worker). ESV is not set up; Lexham (LEB) isn't offered by API.Bible.
- **Bundled Bibles (LEB):** `local: 'bibles/leb'` in `BIBLES`; one JSON per book (`{"<chapter>": [[verse, part, ...], ...]}`, each part a string continuing the paragraph/line or `[kind, "text"]`: `p` paragraph, `q1`–`q3` poetry line, `b` stanza break, `s` section heading, `d` psalm title) generated from a SWORD module with `tools/sword_to_json.py` (run with `python -I` in a throwaway venv with `pysword==0.2.8`). Cached in its own `BIBLES` cache in `sw.js` (so app updates don't wipe it; bump that name when the files are regenerated); it's the default translation for new users, and `prefetchForOffline()` downloads every book the plan uses shortly after load so it truly works offline. Only bundle modules whose license allows free redistribution; check the module's `.conf` (`DistributionLicense`) and add the required notice to `renderNotice()` and `copyright.html`.
- **LEB narration (generated):** `tools/narrate_leb.py` narrates plan chapters with Kokoro (voice `am_michael`) into `OUT/<BOOK>/<ch>.m4a` + `<ch>.json` (`{"verses": [...]}`, same shape as HelloAO timings); setup and run commands are in its docstring. Native CPU on an M4 runs ~10x realtime (faster than MPS or Docker); the plan's 405 chapters are ~27 h of audio, ~400 MB. The output (kept in `~/leb-audio`) is hosted on Cloudflare R2, bucket `daily-reading-audio` under `leb/`, public at its r2.dev URL (the `audio` base in `BIBLES`, also in the CSP's `media-src`/`connect-src`); CORS allows GET from the live site and `localhost:8787`. Upload with `npx wrangler@4 r2 object put daily-reading-audio/leb/<BOOK>/<file> --file … --remote` (`audio/mp4` for `.m4a`). It plays as narrator "Michael (AI voice)" through the same path as BSB narration, online only (streamed, not cached).
- **Commentary:** the book icon in the reader header opens `#commentary`, the Tyndale Open Study Notes (CC BY-SA 4.0) for the open reading, from HelloAO (`/api/c/tyndale/<BOOK>/<ch>.json`, `fetchCommentary()`). Each note is filed under the verse it starts at, with its passage at the start of its first paragraph (shown as a label by `commentaryNote()`); `book.introductionSummary` becomes the collapsed "About <Book>" box. It's shown in the reader's reading-text size and alignment, like the scripture. `commentaryNotice()` and `copyright.html` carry the required credit. It's cached by the service worker once viewed, but not prefetched for offline. Called "Commentary", not "notes", so it isn't confused with the notes people write on marked verses.
- **Copyright:** `renderNotice()` puts the required attribution under copyrighted text, linking to `copyright.html`. API.Bible's Starter plan also requires a visible link to https://api.bible and a linked copyright page.
- **Offline:** `prefetchForOffline()` (shortly after load, and on translation change) waits until the service worker controls the page, then saves the bundled Bible's books, or for HelloAO translations the 30 unread readings nearest today through two weeks ahead. Reading fonts (Literata, Atkinson Hyperlegible; OFL, latin subset) are self-hosted in `vendor/fonts/` and precached. Offline, narrated Bibles read with the device voice (the MP3s are streamed, not cached), and the reader shows `offlineMessage()` for text that isn't saved. Licensed translations never work offline.
- **Caching rules:** free/public-domain and bundled text may be cached offline. API.Bible text may only be cached if refreshed at least every 30 days, kept secure against copying, and deleted within 72 hours if the plan ends, so the app keeps it in memory only.
- **Narration:** `NARRATORS` lists each recorded narrator's Bibles; `narratorId()` uses the saved choice if the current Bible has it, else that Bible's first narrator. For `narrated` Bibles (BSB), `thisChapterAudioLinks` gives human-read MP3s per narrator plus per-verse start times (`*.audioTimings.json`, `verses[n-1]`). `narrateFrom()` plays them in one `<audio>` element, highlighting on `timeupdate`; other translations use speech synthesis. Media Session gives lock-screen controls. Listen buttons start playback only after the text loads, which iPhone Safari blocks outside a tap, so the tap itself calls `unlockPlayback()` (plays `silence.wav` and a silent utterance) to unlock both. (Note: Chrome won't load media in a hidden/background tab, so automated browser tests can't hear playback.)
- **Layout:** every source is turned into the same verse parts (`toVerse()`; HelloAO via `helloaoVerses()`, which reads `poem` levels, `line_break` and headings) and `renderVerses()` lays them out as paragraphs and indented poetry lines with section headings and psalm titles. A verse spanning several lines gets one `.verse` span per line sharing its `data-seg`/`data-ref`. `text` (spoken, shown in the review) leaves out headings; psalm titles are spoken with the chapter heading. API.Bible text is still flat until the `scripture` function returns `parts`.
- **Speech:** Web Speech API, one utterance per verse. `gen` counter invalidates stale utterance callbacks.
- **Reader:** tapping a verse marks it (it does not seek audio; use ‹ ›). "Mark read" closes the reader with an Undo toast; auto-mark after listening keeps it open. Dragging the reader or the commentary to the right closes it, like its back button (`swipeToClose()`).
- **Account UI:** header shows a "Sign in" pill when signed out, or an accent icon with a green dot when signed in; both open the Account screen. A device that was signed in but lost its session shows the `#signin-banner` on load (not after a deliberate sign-out).
- **Marked verses:** tapping a verse in the reader toggles `state.marks['PSA.23.1'] = { i: planIndex, at, t: translationId }`. Only references are stored (never text, so licensed translations aren't cached); the review sheet (`renderReview()`) fetches each verse in the translation it was marked in and shows the required notices. The UI calls them "Verses to discuss" (the week section's button, `#marks-entry` and the review sheet title), since they're for the group meeting. The week section's button reviews that week's marks (shown as a disabled hint when there are none; on meeting day it moves to `#meeting-card`); without a group, `#marks-entry` shows all. Consecutive marked verses (same reading, chapter and translation) form a group (`markRun()`), shown in the review as one row (e.g. 23:2–5) and unmarked together. Unmarking from the review asks first (`#unmark-dialog`), then shows an Undo toast for 3 s inside the review sheet (`#review-toast`; the page `#toast` would sit behind the modal). A group's note (`n`, ≤ 1000 chars, synced with the mark) lives on its first verse; `setRunNote()` consolidates notes when groups merge and `unmarkVerse()` hands a removed verse's note to the rest of its group. Notes are added from the bar shown after tapping a verse in the reader (`#mark-bar`, which also offers Undo after unmarking) or from the review sheet; both open `#note-dialog`. "Ask" links (`askUrl()`) open the AI chosen in `state.ai` (`AI_TOOLS`: Claude, ChatGPT, Gemini, Google AI Mode, or off) with the question in `?q=`, so it runs on the person's own account. Claude project links were tried and dropped: `https://claude.ai/project/…` doesn't open the iOS app, and `claude://claude.ai/project/<id>` opens the project without starting a chat, so the question is lost. Only the reference and translation name go in the URL, never the text. In an iPhone home-screen app (`navigator.standalone`), Gemini and Google links get an `x-safari-` prefix so they open in real Safari (signed in) instead of the in-app browser sheet; Claude and ChatGPT links already hand off to their apps. The choice is synced and chosen in onboarding (`ai` step) or Settings.
- **Onboarding:** `state.onboarded` (synced). Picking a meeting day sets the start to the day after that weekday, on or before the default start (`alignedStart()`; Wednesday → Thu Aug 27, from the default Tue Sep 1), so each group week is 7 full readings; start dates from a share link are kept. Saved state from before onboarding existed counts as onboarded (`load()`). Finishing or skipping marks every reading before the current week (`dueBefore()`) as read so new users start fresh; signing in during onboarding to an already-set-up account calls `window.onAccountRestored`, which ends it without touching their progress.
- **Reminders:** a web app can't schedule its own notification (Notification Triggers was abandoned), so the Edge Function `remind` sends Web Push. pg_cron calls it every 5 minutes with `x-cron-secret` (from Vault); it sends each reminder once per local day, within an hour after its time, naming today's reading from the synced `progress` row and `plan.txt` (fetched from the live site), and skips people who are caught up. VAPID and aes128gcm encryption are implemented with WebCrypto in `webpush.ts` (no dependency); only known push-service hosts are contacted; 404/410 deletes the row. Requires sign-in (the server needs progress) and, on iPhone/iPad, the Home Screen app (iOS 16.4+). Local settings live in `daily-reading:reminder`, not in `state`.
- **Feedback:** Settings → Feedback opens `#feedback-dialog` (code in `sync.js`). Signed-in only (signed out, the row opens the Account screen). Posts `{ message, context }` to the Edge Function `supabase/functions/feedback`, which verifies the user, emails the text (plain text, ≤ 2000 chars) to `FEEDBACK_TO` through Resend from `reading@thewahlstedts.com` with Reply-To set to the sender, and applies a best-effort in-memory 1-minute cooldown per user. `context` is translation, meeting day and whether it's a home-screen app; the function adds the User-Agent.
- **Sync:** `SYNCED_FIELDS` (start, read, translation, automark, meetDay, marks, onboarded, ai, metOn) are synced; marks merge like checkmarks; theme, voice, speed and reading text stay per device. If only the local copy changed, it wins. If both changed, checkmarks are merged (union) and account settings win. A push that would remove many marks or checkmarks compared with the last synced copy (`bigLoss()`: ≥ 8 marks or all of them, ≥ 14 checkmarks or over half) waits for `#sync-guard`: "Keep account's copy" (replaces this device's synced fields) or "Remove them".
- **History:** a trigger (`private.save_progress_history()`, SECURITY DEFINER outside `public`) copies the previous `progress.data` into `public.progress_history` on update, at most once per 30 minutes per person; the cron job `trim-progress-history` keeps 30 days and ≤ 300 rows per person. Users can only read their own rows. To restore someone, find the row (`select saved_at, data from progress_history where user_id = … order by saved_at desc`) and write its `data` back to `progress`; their devices pick it up on next open.

## Conventions

- 2-space indent, single quotes, small functions, sparse comments that explain *why*.
- Colors only via theme tokens (`--bg --surface --ink --muted --line --accent --accent-soft --done --late --highlight`); every UI change must work in all 7 themes, light and dark.
- Phone first: 16px gutters, no horizontal scroll at ~390px wide.
- When changing any cached file, bump `SHELL` in `sw.js`, and add new files to `SHELL_FILES`.

## Security rules (must follow)

- **Never put untrusted text into `innerHTML`.** Use `textContent` / DOM nodes, or wrap values in `escapeHtml()`. Untrusted means: API responses (HelloAO, Supabase), imported files, synced data, device voice names, error messages.
- **All loaded or received state goes through `sanitizeState()`.** That includes localStorage, imports and the sync server. Never spread raw objects into `state`.
- **Content Security Policy** is a `<meta>` in `index.html`. No inline scripts or inline event handlers (`onclick=` etc.); put code in `.js` files. When adding a new external service, add it to `connect-src` (or the right directive) deliberately. Never add `'unsafe-eval'` or `'unsafe-inline'` to `script-src`.
- **Supabase keys:** only the *publishable* key (`sb_publishable_…`) belongs in client code. Never commit or paste the secret / `service_role` keys or the DB password. The DB password is in macOS Keychain: service "Supabase daily-reading DB", account `daily-reading`.
- **Every table gets RLS** with policies scoped to `(select auth.uid()) = user_id`, `TO authenticated`, and explicit `GRANT`s (the Data API does not expose new tables automatically). UPDATE policies need both `USING` and `WITH CHECK`. No `SECURITY DEFINER` functions in `public`.
- **Third-party JS is vendored and version-pinned** in `vendor/` with its license. To upgrade: `npm pack @supabase/supabase-js@<version>` in a scratch dir, copy `dist/umd/supabase.js`, update the `<script>` tag and `SHELL_FILES`, bump `SHELL`.
- **GitHub:** secret scanning + push protection and Dependabot alerts are on; the "Protect main" ruleset blocks force-push and deletion of `main`. Don't disable these.

## Supabase

- Project ref `rnpuwanpgundhfmvzrne` (org "carlowahlstedt's Org", us-east-1, free plan). This directory is linked (`supabase link`).
- Edge Function `scripture`: deploy with `supabase functions deploy scripture --project-ref rnpuwanpgundhfmvzrne --no-verify-jwt --use-api < /dev/null` (it verifies the user itself via `/auth/v1/user`). Secrets via `supabase secrets set` (never in the repo). To test without a user session, temporarily add a bypass guarded by a random `TEST_TOKEN` secret, then remove the code and `supabase secrets unset TEST_TOKEN`.
- Edge Function `remind`: deploy with `supabase functions deploy remind --project-ref rnpuwanpgundhfmvzrne --no-verify-jwt --use-api < /dev/null`. Secrets: `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (from `node tools/vapid_keys.mjs`; the public key also goes in `reminder.js`), `REMINDER_CRON_SECRET` (must equal the Vault secret `reminder_cron_secret`), optional `VAPID_SUBJECT` (`mailto:` or `https:` contact; defaults to the app URL). Changing the VAPID keys makes every device re-subscribe on its next open.
- Table `public.reminders (user_id, endpoint unique per user, p256dh, auth, at_minute, tz, last_sent)`, max 10 per account; cron job `send-reminders` (pg_cron + pg_net).
- Edge Function `feedback`: same deploy command with `feedback`. Secrets: `RESEND_API_KEY` (a Resend key with sending access only) and `FEEDBACK_TO` (the inbox feedback goes to; kept out of the repo).
- Table `public.progress (user_id uuid pk → auth.users, data jsonb ≤ 64 KB object, updated_at)`. Migrations are in `supabase/migrations/`.
- Auth: email sign-in through custom SMTP (Resend, sender `reading@thewahlstedts.com`, configured by Resend's Supabase integration; not declared in `config.toml`, so `config push` leaves it alone). The `magic_link` and `confirmation` templates (`supabase/templates/sign-in.html`) include a 6-digit code (`{{ .Token }}`) and the link; the app's code box calls `verifyOtp({ email, token, type: 'email' })`, which also works in iPhone home-screen apps (they don't share storage with Safari). The hourly email limit (`auth.rate_limit.email_sent`) is dashboard-only.
- New migration: create the file with `supabase migration new <name> < /dev/null` (it reads SQL from stdin and hangs otherwise), write the SQL, then:
  ```sh
  export SUPABASE_DB_PASSWORD="$(security find-generic-password -a daily-reading -s 'Supabase daily-reading DB' -w)"
  supabase db push --linked --yes < /dev/null
  supabase db advisors --linked < /dev/null   # must report no issues
  ```
  Verify the change actually landed (e.g. `supabase db query --linked "<sql>"`), because an empty migration file still gets recorded as applied.
- `supabase/config.toml` mirrors the remote project. **Always run `supabase config diff` before `supabase config push`**: any value declared in the file overwrites the remote, so keep it matching.
- Sign-in email limit is 30/hour (set in the dashboard under Authentication → Rate Limits) and one email per address per minute (`max_frequency`). Free-plan projects pause after about a week of inactivity.
- API.Bible Starter plan (key in `API_BIBLE_KEY`): the 3 licensed Bibles chosen in its dashboard are NIV (2011), NLT and AMP; IDs are in the function's `BIBLES` map. Swapping one means changing the dashboard and both `BIBLES` lists.

## Testing

No test suite. Verify by hand:
```sh
node --check app.js sync.js reminder.js onboarding.js sw.js theme-init.js
python3 -m http.server 8787   # http://localhost:8787 (also an allowed auth redirect)
```
In the browser: no console errors or CSP violations; today card, catch-up, mark read/undo; reader loads and read-aloud highlights verses; Settings (themes, reading text, start date, share link, import/export); a light and a dark theme; ~390px width. Getting started only shows for a fresh browser profile (or after clearing `daily-reading:v1`). **Seed test state only in an incognito window** (the extension needs "Allow in Incognito"), or failing that on `127.0.0.1:8787`, never in a profile signed in to a real account: test state written while signed in syncs over the account. Clear test data afterwards (`daily-reading:v1`, `daily-reading:sync`, `daily-reading:onboard-step`, `daily-reading:invite`, `daily-reading:reminder`). Don't leave test rows in Supabase.
